# Azure DevOps for Command Palette 1.0

The current extension proves that Azure DevOps belongs in Command Palette, but it
still makes you do too much of the setup. You copy URLs from a browser, save them
one at a time, and hope the right account is sitting first in a token cache. When
something goes wrong, a toast may disappear or the extension may look like it
succeeded when it did not.

This specification defines a 1.0 release that starts over where it needs to while
preserving the things people already saved. The extension becomes a focused,
read-only Azure DevOps experience built around discovery, useful project views,
and durable pins.

## Product decision

The product name is **Azure DevOps for Command Palette**.

The provider name inside Command Palette is **Azure DevOps**.

1.0 is for Azure DevOps Services. It is not a general Azure extension. Azure
resources and Azure DevOps have different account models, resource models, and
user expectations. Mixing both into one extension would make the home page harder
to understand and the authentication story harder to trust.

The GitHub repository should be renamed to `CmdPalAzureDevOpsExtension` before the
release candidate. The package identity must not change because existing users
need an in-place upgrade with their local data intact.

## Goals

1. Let a user sign in, choose an organization and project, and find useful Azure
   DevOps content without pasting a URL.
2. Make Assigned to Me, pull requests, favorite queries, and pipelines useful on
   the first visit.
3. Let a user pin durable views to the Command Palette top level.
4. Replace the extension-owned MSAL and WAM stack with the Command Palette
   `OAuthClient`.
5. Keep authentication tokens and cached Azure DevOps content protected for the
   current Windows user.
6. Migrate every existing saved query, pull request view, and pipeline without
   changing what was pinned.
7. Keep pages responsive by showing a recent snapshot first and refreshing only
   the view the user opened.
8. Ship through Command Palette Gallery, WinGet, Microsoft Store, and GitHub from
   one tested set of signed artifacts.
9. Meet the accessibility and localization bar of Command Palette itself.

## Non-goals

The following work is outside 1.0:

* Azure resource management
* Azure DevOps Server and other on-premises installations
* Personal Microsoft accounts
* Cross-organization aggregation
* A project-wide search across unrelated Azure DevOps resource types
* Work item hierarchy
* Editing work items
* Approving or completing pull requests
* Starting or managing pipeline runs
* Any other Azure DevOps write operation
* Service principal, managed identity, or client credentials authentication
* A compatibility authentication stack for older Command Palette hosts

This is intentionally a read-only release. Write operations require broader
permissions, stronger confirmations, more telemetry review, and a different safety
bar. They can come later without holding up a trustworthy 1.0.

## Supported environment

1.0 supports:

* Windows 11
* x64 and ARM64
* Azure DevOps Services
* Microsoft Entra work or school accounts
* The first Command Palette version that implements `IExtensionHost2` and the
  Toolkit `OAuthClient`

When the installed Command Palette host does not support authorization, the
extension shows an upgrade-required page. It does not fall back to the legacy MSAL
implementation.

## Command surface

### Signed out

The top level contains one Azure DevOps sign-in command. Account-specific pins stay
hidden until their account is active.

The sign-in page explains:

* The extension supports work or school accounts for 1.0.
* Browser sign-in is the normal path.
* Device-code sign-in is available when the browser path cannot be used.
* The extension requests delegated Azure DevOps access and only performs read
  operations.
* Tokens stay in the extension process and are protected for the current Windows
  user.

### Signed in

The top level contains:

* One Azure DevOps home command
* Durable pins for the active account

The four permanent areas live inside the home page. They are not four additional
top-level commands.

### Organization and project context

After the first sign-in, the extension discovers the organizations available to
the account.

* If one organization is available, the extension selects it.
* If several organizations are available, the extension shows a picker.
* Manual organization URL entry remains available when discovery cannot find an
  organization the user expects.

The extension then shows a project picker. One selected project scopes the home
page. The last organization and project are remembered per account.

Switching the organization or project updates the home page and cancels work for
the old context. It does not alter pins created for another context.

## Project home

### Work Items

The default view is **Assigned to Me**.

It shows active and non-completed work items assigned to the signed-in account,
ordered by the most recently changed item. An **All assigned** view includes
completed items.

The extension must use the project process configuration to identify active and
completed state categories. It must not hard-code state names such as Active,
Committed, Resolved, or Closed.

Each item shows:

* Work item type
* ID
* Title
* State as text
* Assigned identity
* Last changed time

The primary command opens the work item in Azure DevOps. Context commands copy the
ID or URL.

### Pull Requests

The area contains two first-class views:

* **Created by Me**
* **Needs My Review**

Needs My Review contains active pull requests where the current account is a
reviewer whose vote is still pending. Completed, abandoned, and already-actioned
pull requests remain available through secondary filters.

Each pull request shows:

* Repository
* Pull request ID
* Title
* Author
* Source and target branches
* Review state as text
* Policy status as text when available
* Last changed time

The primary command opens the pull request in Azure DevOps. Context commands copy
the ID or URL.

### Queries

The area shows personal and team favorite queries for the selected project. The
extension deduplicates favorites by query ID and labels whether a favorite is
personal, from a team, or both.

Selecting a query runs it and opens its work items. Pinning the query creates a
durable top-level view.

All saved queries are still discoverable through a secondary browse view. Favorites
are the default because they reflect the set a user already chose in Azure DevOps.

### Pipelines

The area shows pipeline definitions ordered by their latest run. Each definition
shows the latest run status and completion time.

Selecting a definition opens its recent runs. Pinning creates a durable pipeline
view, not a pin to one run.

Each run shows:

* Build or run number
* Status and result as text
* Trigger message
* Requested identity
* Source branch
* Start or completion time

The primary command opens the run in Azure DevOps. A context command copies its URL.

## Search and pagination

1.0 provides search within each area. It does not provide one search across work
items, pull requests, queries, and pipelines.

Each view initially loads up to 50 items. When more results exist, a Load more item
uses the paging mechanism supported by that Azure DevOps endpoint:

* Continuation tokens for pipelines and builds
* `$top` and `$skip` for pull requests
* Client-side windows over the WIQL result IDs for work items
* The query or favorites API's supported paging contract

The page must never restart from the first result while loading the next page.

Search filters loaded results immediately. When an Azure DevOps endpoint supports a
safe server-side filter, the view can issue a debounced request and replace the
results for that search.

Changing the search text, account, organization, project, view, or page lifetime
cancels the previous request.

## Details

Details are on by default for work items, pull requests, and pipeline runs. A
persisted Show details setting can turn them off.

Essential information cannot live only in the details pane. Status, type, and the
information needed to distinguish one item from another must remain available in
the list item title, subtitle, or tags.

## Pins and saved views

A pin represents a durable view. Supported pin kinds are:

* Azure DevOps query
* Repository pull request view
* Pipeline definition

Individual work items, pull requests, and pipeline runs cannot be pinned in 1.0.
Those resources age out too quickly to be useful top-level commands.

Pins are scoped to an account. Only pins for the active account appear. Switching
accounts replaces the visible pin set.

Removing a pin does not remove the saved view. Removing a saved view removes its pin
if one exists. These are local operations and run immediately without confirmation.

## Settings

The 1.0 settings surface contains:

* Active account
* Switch account
* Sign out
* Default organization
* Default project
* Show details
* Telemetry
* Clear cached content
* Copy diagnostics
* Extension and host version

Pin management remains with the relevant views.

## Authentication

### Provider

The extension uses Microsoft Entra OAuth for Azure DevOps delegated access.

The existing Entra application registration uses client ID
`318b152a-4c0e-4050-879d-5e98031c4ccf`. Before implementation begins, the owners
must audit and update that registration:

* Confirm ownership and support contacts.
* Rename and brand it for Azure DevOps for Command Palette.
* Confirm it is a public client.
* Confirm it accepts accounts from any organizational directory.
* Add the loopback redirect supported by the final Command Palette OAuth broker.
* Remove redirects that are no longer needed after the MSAL transition.
* Review Azure DevOps delegated permissions and grant only the permission required by
  this release.

The registration must not contain a client secret.

### Authorization Code with PKCE

Browser sign-in is the default.

The Toolkit `OAuthClient` owns:

* PKCE verifier and S256 challenge generation
* Authorization code exchange
* Token refresh
* Device-code polling

The Command Palette host owns:

* Opening the browser
* Allocating and listening on the loopback redirect
* Generating and validating state
* Returning the palette to the foreground
* Navigating to the signed-in page after the Toolkit reports success

Tokens, authorization codes after exchange, and PKCE verifiers never cross into the
host.

The extension configures the Microsoft identity platform `organizations` endpoints
and requests:

* `openid`
* `profile`
* `offline_access`
* The Azure DevOps `.default` delegated scope for resource
  `499b84ac-1321-427f-aa17-267ca6975798`

Azure DevOps currently exposes `user_impersonation` as its delegated permission and
describes it as full access. There is no narrower read-only delegated permission.
Read-only behavior is enforced by this extension's API clients and test suite, not
by the token scope. The sign-in page and privacy documentation must explain that
difference plainly.

The authentication implementation spike must validate the final scope string and
consent behavior against the audited application registration.

### Loopback compatibility

The OAuth broker specification currently describes a redirect bound to
`127.0.0.1` on an ephemeral port. Microsoft Entra documents port-insensitive
matching for localhost redirects and supports `127.0.0.1` through application
manifest configuration.

The Command Palette OAuth implementation must prove the generated redirect against
the Entra registration before this extension removes MSAL. If the broker needs a
provider-compatible loopback host option, that change belongs in Command Palette,
not in a second listener owned by this extension.

### Device-code fallback

Device-code sign-in is available from the sign-in page when browser sign-in is not
usable. It is not the default.

Microsoft identifies device-code flow as a higher-risk flow, and organizations may
block it through Conditional Access. When blocked, the extension explains that the
organization does not allow this sign-in method and points the user back to browser
sign-in.

The device-code page shows:

* Verification URL
* User code
* Copy code command
* Open verification URL command
* Expiration state
* Cancel command

Polling follows the provider interval and stops on success, expiration, cancellation,
host shutdown, or extension disposal.

### Accounts

1.0 supports one active work or school account at a time.

The stable account key uses immutable token claims such as tenant ID and object ID.
It must not use the email address or user principal name as the primary key.

Switch account starts a new PKCE flow with `prompt=select_account`.

Personal Microsoft accounts are unsupported because Microsoft Entra does not yet
natively issue Azure DevOps resource tokens for them. The extension does not add a
PAT or legacy Azure DevOps OAuth fallback.

### Token storage

The extension implements `ITokenStore` with Windows Data Protection API protection.
The protected payload is stored in LocalState and scoped to the current Windows user.

The token store must:

* Write a new file and atomically replace the previous file.
* Use a versioned envelope.
* Use an account-specific key.
* Validate the protected payload before replacing a known-good token.
* Restrict logging to operation and error categories.
* Remove the account token on sign-out.
* Recover from a missing, truncated, or undecryptable payload by requiring sign-in.

Tokens must never be stored in SQLite, settings JSON, logs, telemetry, crash
attachments, or diagnostics.

DPAPI is used instead of the Toolkit Credential Manager store because a serialized
Entra access, refresh, and ID token set can exceed the small generic credential blob
limit.

### Refresh

Access tokens refresh shortly before expiration. All requests for the same account
share one refresh operation so a busy page does not start several refreshes.

When an API request returns an authentication failure:

1. Refresh once if a refresh token is available.
2. Retry the original safe read request once.
3. If refresh returns `invalid_grant`, revoked consent, or another terminal account
   error, remove the local token and return to signed-out state.

Refresh tokens are replaced whenever Entra returns a new one.

### Sign-out

Sign-out is local to this extension. It:

* Removes the protected token for the active account.
* Cancels in-flight requests and refresh operations.
* Purges fetched Azure DevOps content for the account.
* Hides the account pins.
* Preserves pins, saved views, organization and project choices, and preferences for
  the next sign-in.

It does not call the global Entra logout endpoint or sign the user out of the browser
and other Microsoft applications.

### Upgrade from MSAL

The v2 upgrade requires one fresh sign-in. The extension migrates saved views and
preferences, but it does not ship the old MSAL stack only to translate the existing
cache.

The first run shows an "Authentication was upgraded" message and starts PKCE when the
user chooses to sign in.

After the upgrade is committed, the extension deletes the legacy `msal_cache` file
from LocalState. A failed deletion is reported as a sanitized migration error and
retried on the next launch.

The following legacy components are removed:

* `AccountProvider`
* `AuthenticationSettings`
* `MSALLogger`
* MSAL token cache registration and the legacy cache file
* WAM broker setup
* `AuthenticationMediator`
* Legacy sign-in and sign-out forms and commands

## Runtime architecture

### Composition

The extension uses .NET Generic Host dependency injection. `Program.cs` remains a
small composition root instead of manually constructing the full graph of pages,
commands, repositories, clients, and cache state.

The runtime is divided into these service groups:

* Authentication
* Azure DevOps REST clients
* Account and context selection
* Saved views and pins
* View state and refresh coordination
* Durable storage
* Encrypted snapshot cache
* Settings
* Telemetry
* Diagnostics

Pages depend on application services and view models. They do not construct API
clients or open databases.

### Page state

Each page owns an immutable state snapshot containing:

* Loading state
* Current items
* Continuation token
* Last successful refresh
* Whether the snapshot is stale
* Inline error, if any
* Correlation ID, if any

`GetItems` returns the current in-memory state without disk or network access. A
refresh updates the state asynchronously and calls `RaiseItemsChanged`.

Top-level command generation performs no network or disk I/O. Pins and account state
are loaded before the provider becomes available to the host.

### Lifecycle

Every operation accepts a cancellation token. Page disposal cancels page work and
unsubscribes event handlers.

The runtime must not use:

* `.Result`
* `.Wait()`
* `GetAwaiter().GetResult()`
* `async void` event handlers
* Untracked `Task.Run` calls
* Strong event subscriptions from long-lived services to short-lived pages

The host can dispose and reactivate the extension while an API request or sign-in is
running. Disposal must close listeners, stop polling, cancel refresh, flush safe
state, and return without waiting indefinitely.

## Azure DevOps API clients

The v2 implementation uses typed clients over `HttpClient`. It does not keep the
preview `Microsoft.TeamFoundation*`, `Microsoft.VisualStudio.Services.Client`, or
`Microsoft.VisualStudio.Services.InteractiveClient` packages.

The clients cover:

* Current profile
* Organization discovery
* Projects
* Process and work item state metadata
* WIQL execution
* Work item batches
* Repositories
* Pull requests and reviewer votes
* Query hierarchy and favorites
* Pipeline definitions
* Pipeline runs

Each client:

* Uses a pinned Azure DevOps API version.
* Uses source-generated `System.Text.Json` metadata.
* Accepts a cancellation token.
* Exposes the endpoint's native paging state, including continuation tokens,
  `$top` and `$skip`, or the current window over a known ID list.
* Adds a correlation ID to each logical request.
* Returns typed errors without leaking response bodies into user messages or
  telemetry.
* Uses the active account access token through one delegating handler.

### Retry policy

The extension retries only safe read requests.

It honors `Retry-After` for throttling. Transient connection errors and server
responses can use bounded exponential backoff with jitter. Authentication failures,
permission failures, invalid resources, cancellation, and most client errors are not
blindly retried.

The page shows an inline retry command after the policy is exhausted.

### Favorite query discovery

The implementation spike must validate the supported Azure DevOps favorites contract
for both personal and team favorites. If the favorites contract cannot reliably
return both, the extension may derive the same list from the supported query
hierarchy APIs. The user-facing behavior in this specification does not change.

## Storage

### Durable database

The v2 durable database contains:

#### AccountProfile

* Stable account key
* Display name
* Last active time

It contains no token and no raw identity claims beyond what is required to select the
account.

#### ContextSelection

* Account key
* Organization ID, name, and canonical URL
* Project ID and name
* Last selected time

#### SavedView

* Stable local ID
* Account key
* Organization and project identity
* View kind
* Azure DevOps resource identity
* View options
* Display name
* Canonical URL for opening in Azure DevOps
* Created and updated times

#### Pin

* Saved view ID
* Sort order

#### Preferences

* Show details
* Telemetry enabled
* Other versioned user settings

#### MigrationJournal

* Source schema
* Source table
* Source row ID
* Target saved view identity
* Outcome
* Sanitized failure category

The migration key is `(source schema, source table, source row ID)`. Row IDs are
only unique inside each legacy table.

Database migrations run in transactions and advance one schema version at a time.
Unlike the legacy `DataStore`, a schema mismatch must never delete durable data.

### Encrypted snapshot cache

The extension can persist the latest successful result snapshot for a view.

* A snapshot is fresh for two minutes.
* A snapshot can be shown as stale for up to 24 hours.
* A snapshot older than 24 hours is deleted and not shown.
* Sign-out deletes snapshots for that account.
* Clear cached content deletes snapshots without touching pins or preferences.

Snapshots are protected with DPAPI for the current Windows user. The cache envelope
contains a version, view key, creation time, content type, and protected payload.
Writes use atomic replacement.

The durable database can contain resource IDs and URLs needed to restore a saved
view. Titles, descriptions, branch names, requester names, status details, and result
collections belong in the encrypted snapshot cache.

## Legacy migration

The legacy persistent database is `PersistentAzureData.db` at schema version 4.
Its `Query`, `PullRequestSearch`, and `DefinitionSearch` tables are the migration
source.

The migration:

1. Opens the legacy database read-only.
2. Creates a new v2 database at a different path.
3. Reads every row from all three legacy tables.
4. Parses and canonicalizes modern `dev.azure.com` and legacy
   `*.visualstudio.com` URLs.
5. Creates one saved view per valid legacy row.
6. Creates a pin only when `IsTopLevel` is true.
7. Preserves custom names and pull request view options.
8. Records each outcome in the migration journal.
9. Commits the new database only after the full transaction succeeds.
10. Leaves the legacy database unchanged as a rollback backup through 1.0.

Legacy rows predate the explicit active account model. After the fresh sign-in, the
extension adds the active account key to each imported view. The organization and
project remain the values parsed from that view's URL. A row whose organization or
project cannot be resolved stays in a Needs attention list with its display name
and a repair action. It is never silently dropped.

Repeating migration must not duplicate saved views or pins.

## URL handling

Azure DevOps URLs use one canonical internal form.

The parser accepts:

* `https://dev.azure.com/{organization}/...`
* `https://{organization}.visualstudio.com/...`

It rejects non-HTTPS URLs, unsupported hosts, missing organization or project
segments, and resource types the view does not understand.

Legacy hosts are converted to the canonical connection and browser URL when the
resource can be represented safely. Validation failures remain on the current page,
show a clear message, and never return a success-shaped command result.

This behavior resolves the root cause and silent failure described in issues #154
and #161.

## Errors and feedback

Recoverable errors appear as an inline item in the affected view. The item contains:

* A short plain-language message
* A retry command when retry is safe
* A correlation ID
* A sign-in command when authentication is required
* A permission explanation when the account lacks access

Toasts may supplement success feedback, but a toast is never the only indication of
failure or completion.

Sign-out, clear cache, unpin, and remove saved view execute immediately. The visible
state updates when the operation completes.

Error messages must not display raw exception text, access tokens, authorization
codes, request headers, response bodies, or full URLs.

## Accessibility

1.0 must work with keyboard navigation, Narrator, high contrast themes, text scaling,
and both light and dark themes.

Status cannot depend on color or an icon. Work item state, pull request review state,
policy state, pipeline status, and pipeline result must appear as text.

Use Command Palette glyphs where they express the same meaning. When a custom SVG is
required, provide light, dark, and high contrast behavior and a meaningful accessible
name.

The extension must validate:

* Narrator output for every list item and command
* Logical tab and arrow navigation
* Escape navigation after filtering
* Focus after loading, retrying, changing context, and signing in
* 200 percent text scaling
* Windows high contrast themes
* Status information without images

The extension cannot directly set properties hidden by the Command Palette SDK. Any
missing accessibility contract must be raised upstream and treated as a release
dependency when it blocks equivalent text.

## Localization

Every user-facing string is resource-backed from the first implementation.

1.0 ships the same supported language set as Command Palette. Pseudo-localization
and layout validation run before translation handoff.

Resource strings include accessible names, errors, empty states, telemetry
disclosure, migration messages, diagnostics labels, and OAuth status.

## Telemetry

The extension has its own telemetry toggle in Settings.

* Existing installations preserve their saved choice.
* New installations default to enabled.
* The setting includes a plain-language disclosure.
* Disabling the setting stops new operational telemetry.

Allowed telemetry includes:

* Extension activation
* Authentication flow kind and sanitized outcome
* View kind
* View load latency
* Cache hit, stale hit, or miss
* API category and response class
* Throttling and retry counts
* Migration outcome and item counts
* Pin and feature usage counts
* Sanitized crash signatures

Telemetry must not include:

* Account identifiers
* Tenant IDs
* Organization or project names and IDs
* URLs
* Query text
* Work item, pull request, repository, pipeline, build, or query IDs
* Titles, descriptions, branch names, or identity names
* Tokens, authorization codes, device codes, or PKCE material

PR #102 is not carried forward as-is. The v2 telemetry implementation starts from
this privacy contract.

## Diagnostics and logging

The settings page displays the extension and host versions.

Copy diagnostics creates a sanitized support report containing:

* Extension version
* Command Palette host version
* Windows version
* Process architecture
* Authorization capability
* Active area kind
* Last refresh age
* Cache state
* Recent sanitized error categories
* Correlation IDs

It excludes the same data prohibited from telemetry.

File logging uses structured event names and sanitized properties. Release builds do
not log SQL parameter values, URLs, API response bodies, account names, organization
names, project names, or resource titles.

Logs have a bounded retention period and size.

## Performance

Release targets are:

* Top-level commands perform no disk or network I/O.
* A cached page renders within 250 milliseconds.
* The first live page targets three seconds or less under normal network conditions.
* Pages load no more than 50 items before the user requests the next page.
* API concurrency is bounded per account and view.
* Opening one view does not refresh unrelated saved views.
* A periodic global updater does not run.

Performance tests should measure cold start, warm start, cached page load, first live
load, pagination, project switching, and extension disposal during a request.

## Security and privacy

The extension follows these rules:

1. Treat the installed extension as a public OAuth client.
2. Ship no client secret.
3. Require PKCE for browser authorization.
4. Keep tokens in the extension process.
5. Protect token and snapshot files with DPAPI.
6. Use HTTPS for Azure DevOps and Entra endpoints.
7. Validate organization and resource hosts before sending credentials.
8. Never follow an arbitrary redirect with an Authorization header.
9. Redact sensitive headers and bodies before logging.
10. Use the required Azure DevOps delegated permission, then enforce read-only
    behavior in the typed clients and contract tests.
11. Cancel and discard abandoned authorization state.
12. Treat imported URLs and API content as untrusted data.

A security review is required after the authentication and storage walking skeleton,
then again before the release candidate.

## Testing

### Pull request validation

Every pull request runs:

* Unit tests for parsing, state reducers, settings, paging, retry rules, and
  redaction
* HTTP contract tests with deterministic handlers and recorded response shapes
* Migration tests from real schema v4 fixtures
* DPAPI store tests for round trip, corruption, replacement, and removal
* Upgrade tests that remove the legacy `msal_cache` file
* Authentication state tests with a fake `OAuthClient` boundary
* x64 and ARM64 builds
* Accessibility-focused view model assertions
* Localization resource validation

Tests must not require a live Azure DevOps account on pull requests.

### Scheduled live validation

Scheduled CI runs read-only tests against a dedicated Microsoft-owned Azure DevOps
organization and project. It validates:

* Organization and project discovery
* Assigned work item queries
* Pull request paging and reviewer state
* Personal and team query favorites
* Pipeline definitions and recent runs
* Continuation tokens
* Throttling and permission error mapping where practical

Live failures alert maintainers but do not make unrelated pull requests flaky.

## Packaging and distribution

There is one production package identity.

* Microsoft Store owns the production listing and update identity.
* WinGet points to the Store-backed package.
* Command Palette Gallery consumes that WinGet entry.
* GitHub publishes the same signed MSIX artifacts as a fallback.

The x64 and ARM64 packages are signed and promoted together.

Development builds use a distinct visible name and package identity so they can run
beside the production package. Debug and release builds cannot look identical.

The product uses an approved Azure DevOps logo. Theme-sensitive status icons follow
the accessibility requirements in this specification.

## Release gates

1.0 does not ship with a known:

* Crash
* Silent failure
* Data loss or migration defect
* Authentication state defect
* Token or private content disclosure
* Accessibility blocker
* Broken update path

Additional gates:

* Existing saved views migrate without duplicates.
* Existing top-level state is preserved exactly.
* Rollback leaves the legacy database usable.
* Browser PKCE, device-code fallback, refresh, switch account, and sign-out pass the
  authentication matrix.
* Status is never communicated only by color or icon.
* x64 and ARM64 packages pass the same required tests.
* Command Palette languages are complete.
* Gallery, WinGet, Store, and GitHub install and update paths are verified.
* The release candidate meets the performance targets.
* Scheduled live Azure DevOps tests are healthy.
* Security, privacy, accessibility, and localization signoffs are complete.

The release is quality-gated. There is no date requirement in this specification.
